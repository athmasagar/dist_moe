Mixture-of-Experts, before GPU placement

A Mixture-of-Experts (MoE) layer offers several expert networks, usually MLPs. A router scores the experts for each token and chooses a small subset. Only the selected experts run for that token. Their outputs return to a weighted combine that produces one output row.

Expert parallelism places experts on different GPUs. A selected expert may therefore need a token from a peer GPU and must return its result to that token's owner. Training must also preserve forward values until backward. Routing changes how many expert rows those saved values contain.

Why Dist-MoE also plans activation memory

Dist-MoE combines communication-compute overlap, saved forward state, a fixed memory budget, and CUDA graph replay.

Dist-MoE connects communication and matrix computation with a device-side activation planner. Successive MoE layers pack saved values into one bounded activation slot. When full state would exceed the budget, a layer retains its input and rebuilds intermediates during backward. Its byte offsets and recompute decisions remain on the GPU.

MoK’s current interface includes a shared expert whose local computation can run during dispatch. Dist-MoE accepts routed-expert weights alone and overlaps communication with ready routed tiles. The following hardware view traces one such tile. The memory examples later show how its saved values share an activation budget.

A token can start on one GPU while its selected expert lives on another. Follow a remote BF16 row from its symmetric dispatch buffer across NVLink, into expert-local HBM, through shared memory and tensor cores, and back to the owner’s symmetric combine buffer. The expert’s weights stay local.

Reading the diagrams. HBM is the GPU’s main memory; SMEM is on-chip shared memory; TMEM is Blackwell tensor memory for accumulators. TMA (Tensor Memory Accelerator) stages operand tiles, and MMA is matrix multiply–accumulate. Symmetric dispatch and combine buffers are both peer-addressable device HBM.

This is the central idea: communication and matrix computation are connected by tile-level handoffs. Remote gathering produces local operands; tensor cores consume them; the output epilogue can scatter directly to peers. HBM, shared memory, and tensor memory each play a different role.

01 How does routing assign rows and return addresses?

In the repo’s running example, each expert-parallel (EP) rank is a process with one GPU. Rank 0 starts with A and B and owns experts E0 and E1. Rank 1 starts with C and D and owns E2 and E3. Every token selects two experts. The caller provides those IDs and scores; Dist-MoE has no router inside the expert operation. Use E_e(x) to denote one expert’s result while following the assignment indices.11 An expert is a gated MLP. W13 computes the gate and up projections together, SwiGLU joins them, and W2 projects back to the hidden width.

T counts local input tokens, K counts selected routes per token, D is hidden width, and F is expert intermediate width. R counts the expert-major rows received by a rank. Here T = 2, K = 2, D = F = 256, and balanced R = 4.

Token order and expert order are different

Rank 0’s expert-major input is E0[A, C], then E1[B, D]. A and B are local reads; C and D come from rank 1. Routing metadata creates a source pointer for each expert assignment and a destination pointer for its result. A source token is published once even when several assignments point to it.

Each result returns to its token owner’s combine slot. Its destination pointer contains the source rank, token index, and top-k index. After a GPU barrier, the owner computes Σₖ scoreₖ × h3,ₖ and returns a BF16 [T, D] tensor.

The assignment tells us which expert reads each row and where its result returns. Next, inspect the expert’s internal values and their numerical representations.

02 What values does the expert compute, and in which formats?

Each expert computes two projections with a SwiGLU activation between them. W13 creates gate/up values h1 of width 2F; SwiGLU produces h2 of width F; W2 returns h3 of width D. Forward expert matrix products are called FPROP (forward propagation). These intermediate names will be used throughout the remaining figures.

EACH SELECTED EXPERT · COLUMN-VECTOR MATH

h1 = W13 x = [g; u] → h2 = SiLU(g) ⊙ u → h3 = W2 h2

g and u are the gate and up projections. SiLU(z) = z × sigmoid(z); ⊙ is elementwise multiplication.

BF16 uses two bytes per value. E4M3 has four exponent bits and three fraction bits; its maximum finite magnitude is 448. E8M0 encodes a power-of-two scale in one byte. E2M1 fits a sign, two exponent bits, and one fraction bit into four bits.

MXFP8 stores E4M3 qdata and one E8M0 power-of-two scale per 32 logical values. NVFP4 packs two E2M1 values per byte, stores an E4M3 scale per 16 values, and uses global scales. Quantization is a producer operation: find a scale, round values into qdata, and publish both data and scales for tensor-core consumers. Inspect the small default value, then add the outlier to see the shared scale push it into underflow.

The quantization axis follows the consumer

FPROP consumes activation rows with scales along the contraction columns. WGRAD consumes a transposed activation, so it needs column-oriented qdata/scales along the token axis. These activation bundles are produced separately. A row-quantized forward scale depends on its own row’s contraction block, preserving row-by-row producer readiness. Static MXFP8 weights use grouped 32 × 32 quantization: FPROP and DGRAD can share weight qdata, while their scale orientations remain distinct.

MXFP8 training publishes BF16 source rows and quantizes after peer gather. NVFP4 inference quantizes and packs on the source rank, so the peer reads packed data, block scales, and the row inverse global scale directly. BF16 route outputs return through the same combine protocol.

Qdata, scales, dense intermediates, and padding all consume memory. We can now derive a context budget from these representations and their shapes.

03 How much memory should the context reserve?

The context owns symmetric communication allocations and a separate rank-local activation buffer. The activation buffer holds saved-activation slots and one shared scratch region. Slots preserve forward state; scratch is reused by sequential local actions. Here T is the configured maximum tokens per rank; a call may use a smaller physical count shared by all EP ranks.

With CUDA Virtual Memory Management (VMM), the same contiguous buffer address range has device-backed activation slots, pinned-host overflow scratch, and a hot device-backed scratch suffix. Scratch grows down from the high end. Consecutive virtual addresses can therefore refer to different physical memory tiers. GPU loads and stores use the same buffer pointer. Physical pages are mapped when the context is created and do not migrate during execution. Symmetric dispatch/combine buffers remain separate device allocations.

The minimum budget reserves every layer’s input for replay. Factor 1 adds enough optional-state capacity for balanced full-save. The maximum useful budget is a different reference: full eligible state at the total scratch bound. The factor scales optional saved bytes, independently of the scratch capacity factors.

Scratch sizing counts simultaneously live values and reuse. In BF16, scratch occupied by h2 can overlap later grad_h1 storage after h2’s last read. When D ≤ F, gathered grad_h3 fits an existing gap; D > F needs an additional region. MXFP8 adds row/column qdata and scale storage, including independently padded expert rows.

An allocation sets capacity. The device planner then chooses which forward values to keep. Next, pack successive layers into a slot and watch its recompute decisions, then inspect the individual values’ consumers and offsets.

04 Pack layers, then choose what survives

One context owns a contiguous activation buffer divided into saved-state slots and shared scratch. A slot can hold the saved values of several MoE layers for its current owner. Each forward appends to that slot’s cursor; temporary operands are carved backward from the shared scratch end. A layer does not allocate a fresh activation buffer. max_moe_layers_per_activation_slot sets the depth bound for this stack; its actual saved bytes depend on routing and retention decisions.

Offsets turn one buffer into many tensor views

A planner offset is a device int64 byte displacement from the activation buffer’s base pointer. A kernel addresses a tensor as buffer_base + offset. The device array buffer_offsets[slot] holds the next free byte for that slot, while buffer_offsets[N] holds the scratch end. Each forward records its tensor offsets and resolved physical slot ID for its own backward. Offset zero is valid; the mode flag determines which fields are used.

The recompute choice changes with the live state

The planner tracks cumulative saved bytes per expert-parallel rank. Before keeping a layer’s full eligible state, it reserves enough space to retain the inputs of every remaining layer. It checks the worst rank, so all ranks take the same save or recompute branch even when their received row counts differ.

THE DEVICE’S LOOK-AHEAD DECISION

maxᵣ(saved_bytesᵣ + full_state_bytesᵣ)
+ remaining_layers × saved_input_bytes > slot_capacity

If true, save only source x and write need_recompute = 1. Otherwise, append the eligible state. The input reserve is a budget check, not another allocated tensor.

The default 28 KiB budget keeps the eligible state of L0, L1, and L2. L2's worst-rank candidate plus its remaining-input reserve is 27,136 B, which fits in 28,672 B. L3 would need 35,840 B, so both ranks keep only its source x and replay its expert intermediates in backward. Select “Earlier replay” to tighten the slot to 24 KiB: L2 then replays even though rank 1's candidate would fit, because the worst-rank test fails.

When need_recompute is set, backward republishes the saved input and reconstructs the expert intermediates in scratch. Device predicates gate replay work inside a fixed host launch topology. This budget-driven choice is distinct from h2 being temporary even in BF16 full-save: h2 is always rebuilt from h1 for backward.

Within each slot, matching backwards run in reverse layer order. They restore the saved cursor to that forward’s starting offset, subtract its per-rank saved bytes, and decrement the slot’s layer counter. The slot’s owner may be a stage–microbatch interval or a whole-microbatch interval, as explained in Section 06. Scratch is shared by sequential calls. The context is non-reentrant: concurrent local invocations need separate contexts.

Now inspect one layer’s values and consumers

Backward explains why these values must survive. WGRAD needs the earlier activation operand, and SwiGLU’s derivative needs the gate/up values. Input gradients return to the token owners; weight gradients stay with the expert weights.

Return to the four-token example to make address arithmetic concrete. Use three activation slots, one layer per slot, and either the full-save or minimum-input budget. The precision switch also reveals the effect of per-expert MXFP8 row padding.

Reusing an address at a later time is legal only after the earlier value’s consumers have finished. The diamonds above mark those readers; the matching backward releases the saved region.

The equations use column vectors for one expert route. With h1 = [g; u], SwiGLU produces h2 = SiLU(g) ⊙ u. W2 backward gives grad_h2 = W2ᵀ grad_h3; the activation derivative uses g and u to form grad_h1, and W13 backward gives grad_x_gathered = W13ᵀ grad_h1. Weight gradients sum outer products over expert rows. The token owner sums its input-gradient routes; its route-score derivative reads h3. These are ideal dependency equations: mixed precision approximates the products and rounds stored values.

BF16 full-save retains x_gathered, h1, and h3; it does not retain an additional source x copy. h2 remains temporary and SwiGLU is replayed from h1 in backward. MXFP8 full-save instead retains x/h2 column bundles, dense h1, and h3; row bundles remain temporary in the ordinary Staged path.

The forward also saves its physical slot-ID snapshot. Backward uses that snapshot, not the context’s current selector. This is what lets a later forward select another slot while the earlier backward still finds its own bytes.

The planner decides which bytes survive. Inside a kernel, producer/consumer handoffs decide when a tile is safe to read.

05 How do tiles and warp groups cooperate?

M indexes the expert’s token rows, N indexes projection outputs, and the GEMM’s contraction dimension is tiled independently. A persistent scheduler assigns an (expert, M tile, N tile) to a cooperative thread array, or CTA. One launch covers the local experts. Rows stay within their expert. The block dimensions are tuned compile-time choices; one or two CTAs may cooperate in a cluster. Tail rows and columns are predicated.

Gather first materializes complete source rows of width D in local HBM. TMA then selects a K slice from those rows. For one K slice of C = A × B, the activation operand is BM × BK, the weight operand is BK × BN, and the accumulator is BM × BN. Here BK is a contraction tile width, unrelated to routing top-k K. A and B are consumed to update C, which has its own shape and storage.

Gather warps write source rows into local HBM and signal a per-M-tile counter. The TMA producer waits for that counter before staging A and B into shared memory. SMEM full/empty barriers protect the stages. Tensor-core MMA accumulates in FP32 TMEM; TMEM handoffs protect the epilogue.

For W13 dispatch, the epilogue writes BF16 h1 to local HBM. For W2 combine, the same broad hierarchy ends in direct 16-byte stores to the token owner’s symmetric HBM. A peer barrier then precedes reduction. These are GPU ordering operations, not a CPU read of the routing counts.

From one tile’s handoff to overlapping producer/consumer groups

A GPU warp has 32 threads; a warp group contains four warps. Kernels assign specialized roles to cooperating warps: produce operands, issue MMA, or run the epilogue. MXFP8 adds quantization producers to this hierarchy. Use three 512-row chunks with the same D = F = 256 widths to inspect overlap. Staged forward uses two distributed kernels: dispatch/gather/quantization plus W13, followed by SwiGLU/quantization plus W2/combine. The second launch depends on completion of the first. Mega connects those phases in one chunked kernel topology, using readiness records to coordinate work.

Staged forward can reuse a max-sized row-operand scratch view because the x and h2 producers belong to serialized launches. Mega co-feeds them, so the planner provides disjoint x-row and h2-row subslots. Fusion changes simultaneous lifetimes as well as launch boundaries. A larger backward operand can still set the training scratch peak, so changing the launch policy does not necessarily increase the complete allocation.

Mega training backward also combines DGRAD/WGRAD pairs. WGRAD accumulates in FP32 and writes a BF16 or FP32 destination. Optional direct gradient accumulation requires serialized writers and caller-owned gradient storage.

Within a kernel, readiness protects a tile. Across training microbatches, a longer lifetime protects saved forward state. The framework’s pipeline schedule determines when a whole activation slot is free.

06 When can saved memory be reused?

Pipeline parallelism splits a training batch into smaller microbatches and sends each through model stages. A physical rank can own several logical stages; this example tracks local stages 0 and 2. The pipeline schedule is independent of the Staged/Mega kernel policy.

A stage–microbatch interval starts before one local stage’s forward and ends after that stage’s terminal backward. A whole-microbatch interval starts at the earliest local forward and ends after the last local backward for that microbatch. With split backward, the interval remains live through input backward and ends after weight backward.

A stage–microbatch slot holds one local stage’s MoE layers; a whole-microbatch slot holds all local stages’ MoE layers on the rank. The reserved budget is peak live count × layers per slot × saved bytes per layer. The second tab follows physical-slot ownership, release, and reuse.

These are reserved saved-state budgets for the complete teaching schedule, using the same illustrative 16 MiB per MoE layer. The saving depends on both the schedule’s peak liveness and the layer budget in each slot; fewer live resources alone does not determine memory use.

Intervals are colored once from the finalized schedule: assign the lowest slot whose previous interval has finished. At each forward, the framework selects that slot’s immutable device ID and supplies the layer-depth bound. Dist-MoE consumes the assignment; it does not derive or modify the framework schedule.

Inside a slot, MoE layers append saved state and backward unwinds it in reverse order. The forward’s saved slot-ID snapshot keeps addresses stable through CUDA graph replay and later selector changes. Reset the context after an aborted schedule, once no backward still owns its saved state.

All the pieces now connect: caller routing, peer pointers, the memory plan, typed offsets, kernel handoffs, and schedule-owned lifetimes. The API makes those boundaries explicit.

07 Put the model into code

Initialize an expert-parallel process group, inspect a plan, create the context collectively, and reuse it sequentially. The caller supplies inputs, route IDs/scores, and local expert weights. Close the context after all eager execution and graph replay using it have stopped.

Key ideas from the guide
Dist-MoE
An MoE layer sends each token to selected expert MLPs. Dist-MoE executes those experts across GPUs.
Mixture-of-Experts
The router selects experts and provides route scores. Only selected experts run for each token, and their results are combined into one output.
Execution and memory capabilities
Dist-MoE combines fused routed-expert execution with saved-state packing and budget-driven recompute across layers.
The distributed hardware path
Dist-MoE joins dispatch, expert computation, and combine through GPU memory handoffs.
Caller routing
Routing belongs to the caller. Expert IDs and scores create K assignments for each token while reusing its source row.
Expert order
Gather places local and remote token rows in expert order. Each expert consumes its own contiguous batch.
Return addresses and combine
An expert result returns to its token owner and top-k slot. The owner applies route scores and sums the K results.
The expert MLP
W13 forms gate/up values h1. SwiGLU produces h2, and W2 projects it back to hidden width as h3.
Qdata and scales
Quantized operands travel as qdata and scales. A block’s shared scale changes the rounding of every value in that block.
The quantization axis
Forward GEMMs contract over features, while weight gradients contract over tokens. They need separately quantized row and column activation operands.
Intermediate precision
Operand precision, accumulation precision, and stored-activation precision serve different roles. Tensor cores accumulate in FP32 even when operands are BF16 or block-scaled.
Allocation and VMM
Saved activations stay in device HBM. VMM can extend shared scratch with fixed pinned-host backing in the same virtual address range.
Memory costs
Allocation costs follow tensor shapes, alignment, and the peak of simultaneously live scratch. Slot capacity and scratch capacity use independent policies.
Pack layers into one activation slot
Successive MoE forwards append saved tensor views to one slot. Their backwards restore the saved offsets in reverse layer order; scratch is shared by sequential calls.
Choose saved state or replay from the budget
The device planner checks every rank’s cumulative bytes and reserves replay inputs for remaining layers. If full state exceeds that budget, the layer saves only x and rebuilds its intermediates in backward.
Forward values and backward dependencies
W13 weight gradients read x_gathered, SwiGLU backward reads h1, and W2 weight gradients read h2. The score gradient reads h3; these dependencies explain which values must survive or be rebuilt.
Byte offsets
A tensor view is a byte offset into an existing buffer. Reusing an address is safe after its earlier value’s consumers finish.
Gather and TMA
Gather writes complete source rows into local HBM. Readiness counters then allow TMA to stage the selected A and B slices in shared memory.
MMA and epilogue
MMA consumes differently shaped A and B tiles to update FP32 C. The epilogue converts valid outputs to BF16 and stores them.
One tile through GPU memory and compute
Gather warps publish complete rows in local HBM. The TMA producer stages A/B in SMEM, the MMA consumer accumulates C in TMEM, and epilogue warps convert and store valid outputs.
Producer and consumer coordination
A consumer waits for its operand’s readiness signal. Staged uses launch completion between phases, while Mega coordinates their handoffs inside one kernel.
Chunk readiness
Chunk-local readiness lets downstream work proceed while other chunks remain upstream. Co-live x and h2 operands need separate scratch in Mega.
Producer/consumer readiness by chunk
Mega pipelines gather/quantization, W13, SwiGLU/quantization, W2, and scatter through chunk-local readiness. The full role graph and chunk-state table show what each consumer is waiting for.
Compare lifetimes and peak live counts
A stage–microbatch lifetime ends after that stage’s terminal backward. A whole microbatch stays live until all its local stages finish. Their maximum overlaps are counted before assigning memory slots.
Map lifetimes to reusable Dist-MoE slots
A completed terminal backward releases a slot to a later non-overlapping owner. Releasing one stage is sufficient only under the stage–microbatch policy.
Configuration
Config defines routing dimensions, activation slots, and compute policy. plan_memory resolves the buffer budget before collective context creation.
The public operation
The caller supplies x, route IDs and scores, and local expert weights. A reusable context connects the call to communication buffers and the memory plan.
Documentation and measurement
The public execution guides define the supported paths and lifetimes. Use the package planner and benchmarks to evaluate a real configuration.
